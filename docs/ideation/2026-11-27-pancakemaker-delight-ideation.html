Grounding Context

Codebase Context

pancakemaker is an open-source, offline-first expense tracker (PWA). Data lives in wa-sqlite in the browser, persisted to IndexedDB. Sync is optional and runs through a Cloudflare Worker that relays a sync_log. You can start without an account. Expenses are organised into Personal and Business routes, then panels: a default Daily panel plus seeded Monthly and Annual recurring panels. Categories sit alongside panels, and tags exist in the schema but nothing in the UI uses them.

Already shipped delight: PancakeStack and the Biggest Pancake callout, SparkBars daily spending, a month-over-month badge, Monthly Burn Rate, Spending Pace, 7 demo personas with their own voice, and a desktop keyboard layer (v1.8.0) with a : capture bar, Cmd-K palette, f-hints and month scrub. Recurring panels just gained per-month delete, "This & future", price carry-forward and deterministic copy IDs (PR #13).

Gaps the evidence surfaced:

  • Phones get none of the fast-capture work. The keyboard layer exits on mobile (useKeyboardShortcuts.ts:70).
  • There is no undo anywhere. Deletes use a 2-tap confirm with a 3–5 second timeout.
  • There is no import or restore. JSON export drops IDs, tags and recurring fields (export.ts:31-40).
  • Tags are fully built but nothing calls useTags.
  • Nothing looks forward at upcoming bills or subscriptions.
  • Pace compares only against last month's total, using a straight-line projection.
  • There is no year-level view. Year-to-date was designed in dashboard-b-c-d-design.md but never built.
  • When an exchange rate is missing, convert() silently returns the raw amount.

Not an idea — a bug found while gathering evidence. A recurring expense dated the 29th–31st makes app startup fail. recurrence_day has a CHECK of 1–28, and the generator doesn't clamp it. This was reproduced and is being handled separately.

External context

All from secondary or vendor sources, so moderate confidence:

  • Cashew is loved for being free, needing no bank link, and logging in under a minute.
  • Actual Budget users like local-first, but non-technical users stall at self-hosting.
  • YNAB changes behaviour but carries a steep learning curve and price. Monarch and Copilot are easier but weaker at changing behaviour.
  • Freelancers who mix personal and business on one card call tax time "detective work". They need business-use percentages and accountant-ready exports.

I1. Renewal Radar

I1 Recurring & planned money Confidence 85% Complexity Medium
Description
A forward-looking view of every live recurring series, also shown as a strip on the dashboard. For the next 30, 90 or 365 days it lists name, amount, date and a countdown. When carry-forward picks up a new price, the row is flagged ("Netflix $15.49 → $17.99, +$30/yr"). Annual items get an early warning ("Domain renewal in 23 days · $89") instead of disappearing into the ÷12 burn rate. Each row offers the existing "This & future" stop, and ended series stay visible, struck through, so you can see what you've cut.
Basis
  • direct: the generator already computes each series' next date but only creates copies up to today (recurring-generator.ts:27-36). No upcoming-bills, subscription or budget view exists in source.
  • direct: price history already exists as rows. Carry-forward uses latestLiveOccurrence(original, copies), so a price change is detectable without any new data.
  • direct: annual costs are flattened: const annualMonthly = Math.round(annualYearly / 12) (useDashboardStats.ts:143-152).
  • direct: README.md:14 promises recurring expenses "keep your subscriptions and bills tracked". Today that only looks backward.
  • All five ideation lenses arrived at this independently.
Rationale
Subscription creep is the classic leak nobody notices, and pancakemaker already stores every series' price history without showing it. This turns the recurring engine hardened in PR #13 into something users see and act on. Knowing exactly what's coming is calming, and that feeling is what makes people recommend an app.
Downsides
Only covers expenses the user put in recurring panels. Detecting subscriptions automatically from one-off history is a possible later step, but it's noisier. Needs care so the view doesn't feel like nagging.

I2. "Your Usual": one-thumb capture that learns

I2 Capturing expenses Confidence 80% Complexity Medium
Description
On a phone, the floating + opens a one-line capture sheet instead of the multi-field form. It accepts the same 12.50 coffee #meals grammar as the desktop : bar. Above it sit chips for your most-repeated expenses ("Oat latte 5.25 · Meals"), ranked by how often and how recently you log them. One tap logs the entry. Descriptions you've used before fill in their category from history, so 4.50 coffee logs straight away without a #category. A wrong guess is a one-tap fix on the confirmation toast. QuickAdd remembers your last category. A PWA home-screen shortcut ("Log expense") opens the sheet directly.
Basis
  • direct: the keyboard layer exits on phones: if (!isDesktop) return (useKeyboardShortcuts.ts:70). Mobile only gets a "+" button that opens a form.
  • direct: QuickAdd always starts at the first category: const initialCategoryId = lockedCategoryId ?? categories[0]?.id ?? '' (QuickAdd.tsx:60).
  • direct: "A : line with no trailing #token never one-shots" (capture.ts:78-80). Last-used memory was explicitly deferred in vim-fast-capture-requirements.md.
  • direct: the PWA manifest has no shortcuts (vite.config.ts, verified).
  • external: Cashew is praised for logging in under a minute.
  • reasoned: personal spending repeats heavily (coffee, lunch, transit), much like a café menu, so a tap grid pays off fastest exactly where entries are most frequent.
Rationale
Forgetting to log is how trackers die, and spending happens on the phone, which is currently the slowest way to log. Every logged expense makes the next one faster, all on-device, with no new dependency. This brings v1.8's capture work to the device where most spending happens.
Downsides
Learned guesses can be wrong, so the fix-it chip has to be quick. Web Share Target was left out because it only works on Android/Chromium, and iOS PWAs don't support it. Bundles two moves (a phone capture sheet and learned defaults); they can ship in either order.

I3. Undo, not "are you sure?"

I3 Trust & ownership of data Confidence 85% Complexity Small
Description
Deleting an expense, stopping a recurring series, or editing an amount happens immediately and shows an "Undo" toast for a few seconds, plus Cmd-Z on desktop. This replaces the 2-tap confirm that times out after 3–5 seconds. Undo writes a new forward change (clear deleted_at, or restore the previous value), so it syncs like any other edit instead of rewinding anything.
Basis
  • direct: expense deletes are soft: UPDATE expenses SET deleted_at = ? (queries.ts:410-416), so restoring is a one-column update.
  • direct: there are 0 matches for "undo" in apps/web/src. It was explicitly deferred ("Undo on the confirmation — deferred", vim-fast-capture-requirements.md:87-92).
  • direct: today's safety net is a timer: setTimeout(() => setConfirming(false), offersStopRecurring ? 5000 : 3000) (ExpenseRow.tsx).
  • direct: the toast pattern already exists (CaptureToast).
Rationale
Undo lets people move fast without fear. It removes a step from every delete and makes mistakes cheap. It's the most "feels like a polished app" change for the least code.
Downsides
The evidence check corrected the original pitch. The sync log stores only { id } for deletes, so a full "history with revert" view would need a new log of complete rows; that's a separate, bigger project. Deleting a category or panel removes it for real and cascades, so those deletes keep their confirm, or need extra work to become undoable.

I4. The .pancake file: backup you can restore

I4 Trust & ownership of data Confidence 80% Complexity Medium
Description
A full-fidelity .pancake file: routes, panels, recurring series and end dates, tags, and stable IDs. It's either the SQLite database itself or an equivalent complete JSON. "Open .pancake" restores it on any device, with no account or server. A gentle reminder ("you haven't saved a backup in 30 days") helps people who never turn on sync. In browsers with the File System Access API, people can pick a backup folder once and the app keeps a few dated snapshots up to date. CSV and the current JSON stay as the spreadsheet-friendly export.
Basis
  • direct: export is lossy. formatJSON emits only date, amount, currency, category, panel, type and description (export.ts:31-40, verified).
  • direct: there is no way back in: 0 matches for parseCSV|importData|FileReader|type="file"|restore.
  • direct: the promise it would back up: the manifest tagline "Keep your data" (vite.config.ts:19), and README "all data stays in the browser's IndexedDB". The browser can evict IndexedDB or the user can clear it, and for a user who never syncs it's the only copy.
  • external: Actual Budget is valued for local-first ownership, but self-hosting is the barrier. A portable file gives that ownership with no server.
Rationale
"Local by default" is only reassuring if local data can't vanish. This is the missing half of the app's core promise. It also gives switchers a way in and everyone a guaranteed way out, which matters a lot to people who chose a privacy-first, open-source tool.
Downsides
Restoring into a database that already has data needs merge rules. The second-device merge logic can likely be reused, but it's the fragile area. The File System Access API only exists in Chromium browsers, so other browsers fall back to downloads. A file format becomes something you have to keep stable across versions.

I5. Ghost Pace

I5 Understanding spending Confidence 70% Complexity Small–Medium
Description
Replace the straight-line Spending Pace with this month's cumulative curve, drawn over a "ghost" curve. The ghost is a real past month, or "your normal" (a median of recent months). The headline becomes "Day 14: $212 under your October ghost". Known upcoming bills from the Renewal Radar count in the month-end estimate, so rent on the 1st stops making week one look like a disaster. As an option, the user can drag the "Last month" marker on the pace bar to set their own ceiling. That's budgeting in one gesture, with no envelope setup.
Basis
  • direct: the projection is linear: Math.round((current.totalAmount / elapsed) * days) (useDashboardStats.ts:255-256).
  • direct: the only target is last month: const isOver = prevMonthTotal !== null && projectedTotal > prevMonthTotal (Dashboard.tsx:322). The marker is a plain div titled "Last month" (Dashboard.tsx:349-355).
  • reasoned: recurring bills land on fixed days, so a linear projection is reliably wrong early in the month. On day 3 after $1,500 rent it projects (1500/3)×30 = $15,000. A cumulative ghost has the same lumps on the same days, so comparing the two cancels the bias.
  • external: YNAB changes behaviour but is hard to learn; this aims for the behaviour change without the setup.
Rationale
This fixes the dashboard's main number, which is probably misleading every month for anyone with rent. It also makes pace a game against yourself, like a running watch's virtual pacer, instead of a scolding.
Downsides
Needs a few months of history to be meaningful, so the first month falls back to today's behaviour. The draggable budget line is a product decision: it nudges pancakemaker toward budgeting.

I6. Year in Pancakes

I6 Rhythms over time Confidence 65% Complexity Medium
Description
The year view the design doc planned but nobody built: a 12-month strip, a calendar heatmap of daily spending with no-spend streaks, "same month last year" next to "vs last month", and per-category year totals. {/} scrub years the way [/] scrub months. On the first open of a new month, an optional "flip" card recaps last month: total, biggest pancake, the category that moved, and any price changes. At year end there's a shareable "Year in Pancakes" card in the demo personas' voice. It renders locally with amounts hidden by default, and nothing is uploaded.
Basis
  • direct: "Year-to-Date Summary … New query groups expenses by month for the full year" (dashboard-b-c-d-design.md, section D). Grepping for it returned no matches, and there's no Year view in views/.
  • direct: the only time navigation is addMonths (lib/month.ts). No-spend days are already computed for insights.
  • direct: share machinery exists but only for the demo: navigator.share(...) (demo-share.tsx:29-32) and demo-summary-card.tsx.
  • external: Spotify Wrapped is the reference for a personal-data recap people want to share.
Rationale
Month-over-month is noisy (December always beats November). Long-term users currently get no reward for staying. A year view and a recap moment give them one, and the brand's playful voice finally reaches real users instead of only demo personas.
Downsides
The evidence check had less confidence in the monthly "flip" ritual than in the year view itself; there's no evidence users want a ritual. Ship the year view first and treat the recap card as an experiment.

I7. Lenses & the Tax Envelope

I7 Rhythms over time Confidence 65% Complexity Medium
Description
Use the dormant tag system as lenses: +japan-trip, +kitchen-reno, +deductible. A lens cuts across categories, months and both routes. Each one gets a total, a timeline and its own biggest pancake, and capture accepts +lens tokens. On top of that, a "Tax envelope" export: pick a date range (a quarter or a year) and get a per-category summary plus line items an accountant can use directly, with the +deductible lens marked.
Basis
  • direct: useTags is defined (useTags.ts:5) and nothing outside tests calls it (verified). Tags already sync (reconcile.ts lists tags and expense_tags).
  • direct: export can't be limited to a period: getExportRows(db, userId) takes no date range. There are no tax, deduction or receipt features.
  • external: freelancers on one card face "detective work over 200-400 txns/month", and accountant-ready exports and quarterly reviews are standard advice.
Rationale
"What did the trip or the remodel actually cost?" is one of the most common money questions, and today it takes a calculator. The infrastructure is already built and synced, so this is mostly UI. The tax envelope pays off the Personal/Business split for freelancers, who are pancakemaker's most natural power users.
Downsides
The business-use percentage for split costs (phone 40% business) was left out of this cut. It needs a migration and sync changes for a narrower audience, so it's a natural follow-up if freelancers adopt the envelope. Lenses add a new concept beside categories and panels, so the UI has to make the difference obvious.

Rejection Summary

# Idea Reason Rejected
R1 Honest currency / Passport Mode (each expense at its own date's rate, trip mode) Split. The silent raw-amount fallback in convert() is a correctness bug to fix directly ("~ 3 amounts not converted"), not a feature. Historical per-date rates need an online, rate-limited service and new caching, which is too costly for the value for now.
R2 Business-use % split ("Split Pancake") Weak as bundled. It needs a migration and sync changes for a narrow audience. Its cheap, strong part (date-ranged export) survives inside I7; the split is a follow-up.
R3 Change history / "Time Machine" with revert Basis corrected by the evidence check. sync_log stores only { id } for deletes and is pruned after 7 days, so it can't power history or revert. It would need a new log of complete rows. Its strong part (the undo toast) survives as I3.
R4 One journal powering undo, history and point-in-time backups Same correction as R3. Today's log holds partial entries and is pruned, so this would need a new table and storage growth.
R5 = query bar ("= coffee since june") Weak. The palette index is capped at the 50 most recent expenses, a query language is scope creep, and the value overlaps I5 and I6.
R6 Statement Reconcile (bank CSV used to find unlogged expenses) Feasibility trap: parsing many bank CSV formats plus fuzzy matching is a lot of effort. Could come back once I4 creates a file-import surface.
R7 Zero-knowledge (end-to-end encrypted) sync Weak for now. Magic-link auth gives no password to derive a key from, and key management with no recovery path touches the most fragile area (sync). The opaque-payload design keeps it possible later.
R8 Shared stack (household/trip panel with settle-up) Refuted. It needs multi-user ledgers, invites and conflict handling, which contradicts the single-user sync model.
R9 Month-close ritual combined with historical currency Weak combination that stacks R1's cost onto an unproven ritual. The month recap survives as an optional part of I6.
R10 Web Share Target / capture URL as the main phone entry Narrowed. Share Target is Android/Chromium-only and missing on iOS PWAs. The PWA shortcut survives inside I2.
R11 Automatic subscription detection from one-off history Merged into I1 as a later step. Inferring recurrence from descriptions is noisier than using recurring panels.
